# Local App Contract

Status: 2026-10-06 implementation contract, with batch saving on in-app departure, manual Issue saves, same-computer shared SQLite storage, and separated attachment content. User decisions in requirements.md take precedence. The first build connects catalog, standards, purchasing, inspection, issues, library, reporting, and backup through one durable local workflow.

## Public interface

`core/qc-service.js` exports `createQCService(adapter, options?)` for server-side business execution. `core/qc-app.js` composes and exports an HTTP service facade as `qcService` for browser callers. The facade preserves the public service interface. All public operations are asynchronous:

- `initialize()` opens storage and creates the empty catalog state only if absent. Existing imported history is upgraded atomically to canonical historical batches once. It applies a narrow, audited, idempotent status correction to the two exact AP `25.10.29` PDF-derived version IDs, guarded by family, label, source marker, and prior status. When a matching recorded source entry is present and verified, it moves linked documents to that entry, removes the duplicate from active `versions`, and retains its full superseded record in optional merge evidence. A missing recorded target leaves that pair unchanged for older PDF-only workspaces. It also applies the audited `correctHistoricalPdfRecords` correction once: printed bare-number defective rates and printed zeros are restored, a color stated for only part of a historical batch is unassigned with a partial-allocation anomaly, mislabelled AP/UI duplicate anomalies are removed, machine-specific source fields are dropped, and derived historical batch projections are rebuilt. Each rule applies only while the stored value equals the known incorrect value; staff-entered results, attachments, and Issues are never changed. It also removes the single authorized S15 trial source version only when ID `lark:recvwbnjOo2r4P:s15`, source ID `recvwbnjOo2r4P`, family `s15`, label `26.09.05`, description `fefe`, and empty specs and attachments all match. If a batch or other dependency references that version, initialization rejects without a cascade or partial deletion. No other versions are archived or deleted by date, status, or label. No sample orders, batches, results, or signatures are installed automatically. Full-mode initialization follows the full-read limit described in the attachment limits section; the browser and the snapshot restore check use `{ mode: "lightweight" }`.
- `getState()` returns an isolated full state snapshot for compatibility, but only while the stored attachments total no more than 50 MiB (`BACKUP_MAX_BYTES`) of decoded content. Above that it fails with code `content_too_large` before any attachment body is read, and the message points to the database snapshot. `getState({ mode: "lightweight" })` returns business records and attachment metadata (including `decodedBytes`) without Data URLs, with no size limit. Browser initialization uses the lightweight mode. `getAsset(assetId)` returns one complete attachment (at most 20 MiB) on demand.
- `command(type, data, expectedRevision)` validates current state and writes atomically; returns `{ entityId, revision }`, with a `changes` projection for manual field saves and purchase-order saves. Each projection contains saved records and newly added audit events. The frontend applies it without a full-state reload. A supplied stale revision rejects with an actionable reload message. Frontend supplies its current snapshot revision.
- `getBatchWorkspace(batchId)` returns the batch, a query-only `displayNumber`, related entities, resolved product allocations, rows, release blockers, and resolved batch attachments. `displayNumber` is outside the persisted batch object. Operational rows include their product label, quantity and locked version, legacy photos, resolved `{ videos, procedures, log }` attachments, every linked Issue with its resolved evidence files, and up to four saved older results for that product variant. Historical workspaces preserve source values and provenance; unknown related entities remain null.
- `resolveBatchDisplayNumbers(state)` in `core/qc-batch-display.js` returns a `Map` from batch ID to staff-facing name without changing state. It resolves collisions against the complete batch collection before any UI filtering or sorting.
- `getPurchaseOrderProgress(orderId)` returns `{ order, lines }`; each line includes `variant`, `orderedQty`, `releasedQty`, `remainingQty`, `excessQty`, and contributing `batches`.
- `exportBackup()` returns a JSON-serializable `{ format: 'masterqc-web-backup', formatVersion: 1, exportedAt, state }`, including attachments. The Backup and restore page no longer uses it; it remains for compatibility and tests because every payload must be serialized in memory. It fails with code `backup_too_large` when the serialized JSON would exceed the 50 MiB that restore accepts, so an export never produces a file that restore refuses.
- `createSnapshot(targetPath)` writes one consistent SQLite copy of the whole workspace (records, attachments, and revision) to a new file with `VACUUM INTO`. It rejects an existing target and the live database path. The memory adapter does not support snapshots and fails with a clear error. The HTTP route `GET /api/qc/<workspace>/backup/snapshot` writes a temporary snapshot in the data directory and streams it as `application/vnd.sqlite3` with `Content-Disposition: attachment; filename="masterqc-<workspace>-<UTC timestamp>.sqlite"`. The temporary file is deleted after the response, a client disconnect, or an error. Snapshots have no attachment-size limit; this is the full-workspace backup for workspaces larger than 50 MiB. Requests with a foreign `Origin`, or a `Sec-Fetch-Site` other than `same-origin` or `none`, are rejected with 403; Host checks still apply.
- `importBackup(backup, expectedRevision)` validates the full graph before an atomic, additive import. Exact verified AP duplicates in older backups are reconciled into an available matching recorded entry. It filters the exact guarded S15 trial record from older backups and applies the same dependency check to an existing active copy, so the trial cannot be restored; if referenced by a batch or other dependency, restore rejects without a cascade or partial deletion. Other identical IDs with identical content are skipped; conflicting IDs reject without changes. This operation never clears or overwrites other existing data. Stored attachment bodies are loaded only for IDs that the backup repeats, so comparison work follows the backup rather than the workspace total. It returns counts and the new revision.

Errors throw `Error` with English user-facing messages. No DOM or browser dialogs belong in core. Empty strings, nulls, fractions, non-finite quantities, and invalid references must be validated before committing. Reads return copies. Dates use `YYYY-MM-DD`; event timestamps use ISO timestamps.

`core/qc-service.js` also exports the attachment and request limits: `PHOTO_MAX_BYTES` (20 MiB), `DOCUMENT_MAX_BYTES` (20 MiB), `ASSET_TOTAL_MAX_BYTES` (500 MiB decoded payload), `BACKUP_MAX_BYTES` (50 MiB serialized JSON), `UPLOAD_REQUEST_MAX_BYTES` (64 MiB decoded file content per upload request), and `API_UPLOAD_BODY_MAX_BYTES` (the HTTP body limit for upload commands). `core/qc-app.js` exports `createDemoQCService()` for the separate, explicitly labelled demo workspace.

## State

SQLite stores business records in `qc_records` and `qc_units`, and attachment content in `qc_asset_payloads`, per isolated workspace; `qc_state` keeps the revision and storage marker. Business asset metadata retains a stable `masterqc-asset:v1:<id>` content reference. The server validates expected revision and the business graph inside one transaction before committing; ordinary field saves do not reconstruct every attachment. Full reads and JSON exports still expose the original Data URLs, but only up to the full-read limit in the attachment limits section. Validated payload metadata and a transactionally maintained payload-generation counter prevent repeated decoding while detecting content changes from other connections. Payload metadata rows are cached per payload generation, so ordinary saves do not walk attachment storage. New, replaced, imported, and restored content receives complete validation. Legacy inline state upgrades atomically after creating a verified `<databasePath>.pre-attachment-payload-migration.sqlite` recovery copy, preserving the original state, revision, and attachment bytes. The single-row business JSON of the previous format converts once to record storage after a verified `<databasePath>.pre-record-storage-migration.sqlite` recovery copy; the conversion commits only if the rebuilt aggregate matches the original, including revision. The previous IndexedDB stores remain untouched. Direct browser migration and the retired initialization draft and AP table prototype are removed. Existing full JSON backups remain compatible with validated additive restore, preserving identifiers and evidence without silently replacing a populated SQLite workspace.

State is `{ schemaVersion: 1, revision, families, variants, versions, orders, batches, issues, assets, audit, versionMergeEvidence? }`. Collections are arrays; IDs are stable strings generated with UUIDs. Initial catalog contains families `s11-s14` and `s15`, models S11–S15, and standard-red and Yellow variants. Display names omit Red. The latest-published query remains published-only and sequence-based. The new-batch default considers existing `recorded`, `published`, and `superseded` versions, ordered by `effectiveDate` or a recorded entry's source effective timestamp, with sequence as a tie-breaker; mutable `draft` versions are excluded.

- Family: `{ id, name, models: string[] }`.
- Variant: `{ id, familyId, model, color, label, active }`; `label` is the displayed name. Extra minor variants may be added with a distinct label.
- Operational version: `{ id, familyId, label, sequence, effectiveDate, status, notes, items, createdAt, publishedAt }`. `status` is `draft`, `published`, or `superseded`; `sequence` is a positive integer unique within the family and determines numeric ordering. Published and superseded versions are immutable. Published-version ordering continues to use sequence for its existing query. Superseded versions are eligible for new batches, including when `publishedAt` is null. An imported Lark source version uses `status: "recorded"`, `sequence: null`, `effectiveDate: null`, `createdAt: null`, `publishedAt: null`, and `items: []`; its original facts live in `source` and `sourceRows`. These records are immutable evidence, not Web drafts or published standards. Their source effective timestamp, raw status, exact label, change description, linked spec values, nulls, and attachments metadata remain unnormalized in the source payload. Recorded versions have no operational sequence but are eligible for new batches: core projects the linked source rows into the batch snapshot without changing `items`, `source`, or `sourceRows`, and without publishing or rewriting the record.
- Standard item: `{ id, key, no, title, titleZh, specification, specificationZh, devices, factory, stage, models, samplingPercent, recordingRule, important, timeSeconds, procedureUrl }`. `important` is the persistent importance flag for this versioned standard item; green indicates importance, not pass/fail. `models: []` means all models in the family. `key` is the stable historical comparison identity. Sampling is numeric and independent of the descriptive recording rule. Item IDs remain stable through editing/cloning unless explicitly adding a new item.
- Order: `{ id, number, date, supplier, notes, lines, createdAt }`; line: `{ id, variantId, orderedQty }`. Order numbers are unique. Referenced lines cannot change variant or be removed.
- Operational batch: `{ id, number, orderId, products?, lineId, variantId, familyId, quantity, factory, stage, lotNumber?, countForPO, versionId, versionLabel, date, recorder, notes, status, rows, createdAt, releasedAt, attachmentIds? }`. Number is unique and remains in the existing saved field. Core generates it for a new command with an omitted or blank number as the distinct product models, sorted deterministically and joined by `+`, followed by `-YYYYMMDD-<normalized factory>-<normalized stage>`. A case-insensitive collision with stored numbers or resolved historical display names adds the first available `-01`, `-02`, and subsequent suffix. Legacy commands may still supply an explicit number; saved values are not rewritten. New batches contain `products: [{ lineId, variantId, familyId, quantity, versionId, versionLabel }]`, with unique lines from one PO, variants of one model, and a safe positive integer quantity per color. Existing mixed-model records remain valid; the restriction applies to new commands only. The canonical `createBatch` command supplies one top-level `versionLabel`; core resolves that exact common label to each selected family's eligible version entity and saves those family-specific IDs in the product allocations. The top-level quantity is their sum. Single-product identity and version ID mirror that product when there is exactly one; those identity fields and `versionId` are null for a multi-product batch. A new shared-version batch retains its common `versionLabel` at the top level. Older mixed-version multi-product records retain a null top-level label and their independent nested version IDs. Existing records without `products` retain their original single-product fields. Core normalizes both shapes through pure queries without rewriting saved records. New batches need no physical lot identifier; preserved non-empty legacy lot values retain their existing duplicate-counting checks. For every new batch, core derives `countForPO` from the stage: OQC is true and IQC is false. Callers cannot opt out of counting a new OQC batch. Previously saved flags remain unchanged. A released counting batch contributes each product's quantity to that PO line. Omitted `attachmentIds` in older data means no batch documents. Attachments are optional and independent of row photo ownership.
- Batch row: all standard-item fields plus `{ inspectedQty, defectiveQty: null, actualTimeSeconds: null, remarks: '', savedAt: null, photoIds: [] }`. Batch creation copies each applicable version item's fields, including `important`, into the locked row for each selected variant. Ordinary result saves cannot change these standard fields, and later version edits or clones do not rewrite existing batch snapshots. New product rows also contain `{ productLineId, sourceItemId }`: a fresh unique row `id` owns results and evidence, while `sourceItemId` preserves the original locked standard-item identity. New rows may also have `attachmentIds: { videos: id|null, procedures: id|null, log: id|null }`; older rows omit it and remain unchanged. Each slot owns one `rowAttachment` asset and cannot share it with another row or Issue. `inspectedQty = ceil(product.quantity * samplingPercent / 100)` is locked with the row; legacy rows use their single batch quantity. Complete row saves require finite numeric `actualTimeSeconds >= 0`, allowing decimals. Partial row saves accept null measured time and defective quantity for incomplete rows, preserve remarks for old records and callers, and clear `savedAt` while either numeric result is absent. A legacy row that truly omits `actualTimeSeconds` may receive a partial save without that field; core preserves the omission and its historical completion rule. Current rows with an explicit measured-time value, including `null`, require the field in every partial save. Partial values remain valid backup data; only completed rows provide release and history eligibility. Issue creation can link any editable operational row and preserves its persisted blank or partial results without saving browser drafts. It is an entered result independent of the locked standard `timeSeconds`. Older rows and backups may omit it; missing values are not filled from the standard or zero. New issue snapshots and operational reports preserve the entered time. Defective rate is derived by core; zero inspected quantity gives null rate. Product allocations, standards, and batch identity/quantities are immutable after creation; recorder, date and notes remain editable until release.
- Issue: `{ id, number, title, reportedBy?, description?, requestId?, requestFingerprint?, attachmentIds?, batchId, rowId, sourceSnapshot, status, owner, disposition, confirmations: ['', '', ''], discussion, createdAt, closedAt }`. Every newly created Issue requires a manually entered, trimmed `reportedBy` name of at most 200 characters and at least one uploaded raster photo; a general file or legacy row-photo snapshot alone does not satisfy the photo requirement. Older Issues and backups may omit `reportedBy`; preserve that omission without inventing a name. New Issue creation may also supply an optional initial disposition `owner`, trimmed and limited to 200 characters; blank or omitted values save as an empty `owner`, while invalid types or longer values reject atomically. Later disposition saves may change or clear `owner`. Existing Issues and backups may omit Issue attachments and remain unchanged. Standalone issues use null source IDs; optionally associate them with a batch. New batch-linked snapshots contain `products: [{ lineId, variantId, variantLabel, quantity, versionId, versionLabel }]`; single-product metadata is null for a multi-product batch. A row-linked snapshot additionally preserves the actual product's line, variant, family, quantity and version within `sourceSnapshot.row`. Row snapshots allow null defective quantity, measured time, and saved time when results are incomplete; the rate remains null when defective quantity is null or inspection quantity is zero. Snapshot results are immutable saved facts and do not include unsaved browser edits. Existing single-product snapshots remain valid. Several Issues may link to one batch and row when each is created with a distinct request ID; the request fingerprint includes the trimmed reporter and any nonblank initial owner, so retries must match both creation values even if the saved disposition owner has since changed. Blank or omitted initial owners retain the existing fingerprint calculation for compatibility; a mismatched reuse of the ID is rejected. Callers without a request ID retain the legacy singleton behavior for a batch and row. Additional Issue attachments can be added later. Each new discussion entry requires a manually entered, trimmed nonblank `authorName` of at most 200 characters. Legacy entries may omit `authorName`; preserve them without backfilling a name. If present, the stored name must be valid nonblank text. Closing requires owner, disposition and all three names, then an explicit action. Closed issues are read-only except for deletion where allowed. `deleteIssue` removes an open or closed standalone or operational Issue and only its owned `issueAttachment` assets; source snapshot photos and row attachments remain. It rejects Issues linked to released or historical batches and never releases a batch as a side effect.
- Asset: `{ id, name, mimeType, dataUrl, kind, batchId, rowId, versionId, createdAt, issueId?, category? }`. Existing `photo` and `document` kinds remain valid. A `rowAttachment` has `batchId`, `rowId`, and category `videos`, `procedures`, or `log`; it exclusively owns that inspection-row slot. An `issueAttachment` has `issueId`, and its nullable batch and row IDs must match its Issue; category is `photo` or `file` and preserves the applicable per-file limit. Library documents may associate with a version. Supported general files include PDF, PNG/JPEG/WebP/GIF, text/CSV/Markdown/log, DOC/DOCX/XLS/XLSX/PPT/PPTX, ZIP, and MP4/MOV/WebM. Active web content, executable files, SVG, and macro-enabled Office formats are rejected. Keep 20 MiB per photo, 20 MiB per general file, document, video, or batch attachment, 500 MiB total assets, and 50 MiB per JSON backup or historical package; no attachment-count cap is imposed.
- Optional version merge evidence: `{ id, targetVersionId, version }[]`. Each entry preserves the complete superseded PDF-derived operational record removed by the exact AP merge. This backup-only collection is not shown as a separate version or selectable batch choice; older state and backup files may omit it.
- Audit entry: `{ id, at, action, entityId, summary }`. Business mutations append an event for local traceability; this is not authenticated identity verification.

## Frontend ownership and integration

The root entry is `frontend/index.html`, loading `frontend/qc-main.js` and `frontend/qc.css`. The retired initialization draft and AP table prototype pages and their dedicated files are removed. Backup and restore has no Reference pages disclosure.

Shared UI helpers live in `frontend/qc-ui.js`: safe DOM creation (`el(tag, props, ...children)`), `field(label, input)`, `button(label, handler, className?)`, `showDialog(title, content)`, `closeDialog()`, `notify(message, error?)`, file-to-data-URL and download helpers. Use textContent for user content, never unsanitized HTML. The owner of the main shell provides these helpers.

Each family in the Standards page has one `Versions` list. It displays internally recorded source entries first in source effective-date order, then operational versions in numeric sequence order. The two exact verified AP `25.10.29` PDF-derived duplicates are consolidated into their matching recorded entries, with the original PDFs linked to those recorded cards; the removed records remain only in optional backup merge evidence. Draft cards retain edit, publish, and item-view controls. Published and superseded operational cards use a compact read-only layout with inline attachment links, their status, effective date, and a `Change description` disclosure. Superseded cards show `Status: 已作废 Superseded`; neither published nor superseded cards have right-side actions, clone controls, or item tables. Standards shows no `Latest` badge or latest-published heading. The disclosure uses `visibleVersionNotes` to show ordinary business notes; it is blank for generated reference notes or empty notes, and saved notes are not changed. Each card places its attachment control beside its label. If no document is linked, the control offers Upload attachment. If one or more are linked, each filename is a compact preview link and upload stays hidden until all are removed. The viewer previews PDFs in a blob-backed iframe, images as images, and text through safe text content; it also offers Download and a confirmed Delete action. Upload uses `addDocument` with the card's version ID, existing supported document types, and the 20 MiB per-document / 500 MiB aggregate limits. `removeVersionAttachment` verifies ownership; it deletes an unreferenced asset or clears `versionId` while preserving assets referenced by batch attachments or historical sources. This does not alter version facts, source evidence, or schema version. Recorded cards show their label, status, effective date, change description, and linked documents. The business UI omits extraction-origin labels, provenance, anomaly details, and raw revision fields. It also omits generated reference notes beginning `Historical source reference draft.` or `masterqc-ap-oqc-reference-25.10.29.` from cards while keeping ordinary staff notes visible. Recorded descriptions may receive display-only line breaks; the `VENTUS` label filter and generated-note omission do not change persisted records or backups.

Admin pages export `renderAdminPage(root, route, ctx)` from `frontend/qc-admin.js`; routes: `catalog`, `standards`, `orders`, `library`, `settings`, `backup`. Both `settings` and `backup` display Backup and restore directly, with a matching bottom-sidebar label. Operations pages export `renderOperationsPage(root, route, ctx)` from `frontend/qc-operations.js`; routes: `batches`, `batch-report`, `issues`. Issue list rows open the detail on click or keyboard Enter/Space; the list has no separate Open action column and searches the stored reporter name. The Issue detail shows `reportedBy` as read-only source metadata, separate from disposition owner and discussion contributors. Its Evidence section shows uploaded Issue photos as constrained inline thumbnails with keyboard-accessible Preview, Download, and Remove controls. Immutable inspection source photos remain in their separate source section, which is hidden when the snapshot has no photos. The shared Create issue dialog, including standalone and inspection-row entry, offers an optional Initial disposition owner field. The report is a child route of Batches at `#/batches/<encoded batch ID>/report`; it has no sidebar item or separate report list. Legacy `#/reports` redirects to Batches, while `#/reports/<id>` redirects to that batch's report. Every historical, draft, and released batch detail provides **View report**; **Back to batch** returns to the same detail. Reports show saved workspace values only, with Print / save as PDF and CSV export. `ctx` is `{ service, state, navigate(route, id?, force?), refresh(), run(type, data), selectedId }`. `run` executes using current revision, updates the state and renders; errors are displayed without discarding form inputs. Modules may obtain fresh queries from service, but never access storage directly.

`ctx.run` returns `{ ok: true, result }` or `{ ok: false, error }`; modal callers close only on success. File helpers are named `readFileAsDataURL(file)` and `downloadFile(name, contents, mimeType)`.

## Historical batches and source evidence

The optional `state.history` object contains `sources`, `inspections`, and `anomalies`. States and backups without this object remain valid. These collections preserve transcription evidence. Each imported inspection also has a canonical entry in `state.batches`, shown in the same Batches workspace as newly entered inspections. The evidence collection is not a separate user-facing PDF history module.

Historical batches have `kind: 'historical'`, `status: 'historical'`, and `historyInspectionId` equal to their stable source inspection ID and batch ID. ## Shared Local Service Contract (2026-09-30)

- The browser uses same-origin JSON HTTP calls. The server executes existing core methods; browser code cannot directly write SQL or replace state.
- Production and demo workspaces are explicitly allowlisted and separate. The server binds to `127.0.0.1:4173`, checks Host and Origin, and rejects unsupported operations, oversized payloads, and invalid JSON request types. Body and full-read limits are listed in the attachment limits section below.
- Every browser mutation sends its observed revision. A stale revision fails without committing; clients must reload before retrying. Main-app operations do not modify the source IndexedDB.
- Direct browser migration is retired. Existing full JSON backups remain restorable additively through the shared service. Legacy browser data remains untouched.
- Saved records survive browser reload and server restart. Batch inspection and metadata save automatically before in-app departure, without a Save changes button; Issue disposition retains explicit Save changes and Save/Discard/Cancel exit choices. Input/change/blur never submit. Batch navigation waits for all edits to be acknowledged, including typing during a save. Invalid or failed saves keep the page open with the draft and an explanatory error. Browser refresh and tab closing use the native unsaved-change warning and do not save. Discussion and attachments remain separate explicit operations. Local service availability is required for reads and writes; failures must not fall back to a disconnected browser database or report a successful save.

## Attachment, request, and full-read limits (2026-10-16)

- Per file: every attachment category accepts up to 20 MiB of decoded content. Stored attachments total at most 500 MiB; the total is checked from stored sizes before any write, and an exact fit is accepted.
- Upload budget: one upload request may carry 64 MiB of decoded file content (`UPLOAD_REQUEST_MAX_BYTES`). The browser sums the File sizes of the selection before it reads anything (**New issue** and **Add files** on an Issue) and asks for fewer files when the total is larger. Batch attachments, row attachments, and library or version documents send one file per request, which the per-file limit already bounds.
- HTTP body limits: `initialize` and `command` accept up to `API_UPLOAD_BODY_MAX_BYTES` (86.3 MiB, the base64 text of 64 MiB plus 1 MiB for JSON envelopes). `restore` and `history` accept up to 50 MiB plus a 4 KiB envelope. A body larger than its limit, declared or streamed, returns 413 with code `body_too_large`; the upload message asks for fewer files at a time.
- Full-content reads: `getState()` without the lightweight mode, a full `initialize`, and a full `getBatchWorkspace` return 413 with code `content_too_large` when the stored decoded attachments exceed 50 MiB (`BACKUP_MAX_BYTES`). The decision uses stored sizes and never reads an attachment body. The message points to the lightweight state, single-attachment reads, and the database snapshot. Lightweight reads, `getAsset`, and snapshots are not affected.
- JSON exports: `exportBackup()` and `GET /api/qc/<workspace>/backup` return 413 with code `backup_too_large` when the serialized backup would exceed 50 MiB. The estimate counts Data URLs as base64 text and errs toward refusal, so an export never produces a file that restore would refuse.
- Commands read stored attachments as metadata only. This includes `importLarkVersionHistory`, which previously loaded every body. Restore and history imports load bodies only for attachment IDs that the incoming package repeats.
- Validation cache: the content-parse cache retains at most `MAX_ASSET_VALIDATION_CACHE_CHARS` (64 MiB) of Data URL text, independent of the workspace total. A maximal 20 MiB file is about 28.0 million characters, so two such payloads stay cached; a larger payload is parsed each time and never retained.
- Legacy inline databases from before the payload table still parse their whole aggregate once during their one-time conversion. The current production file already uses the payload table.

## Portable Project Database

Default production persistence is `data/workspace/masterqc-main.sqlite`. The file includes the complete aggregate and attachment payloads and is eligible for Git. Demo data and temporary SQLite journal files remain ignored. A `MASTERQC_DATA_DIR` override changes the storage directory without rewriting or importing another existing database. The workspace directory is never statically served.

SQLite DELETE journaling with FULL synchronization retains completed commits in the main file. Stop the service before copying, committing, pulling, or replacing it because file-copy tools and Git do not take SQLite transaction locks. A clone containing the file opens the same saved state; no sample installation or automatic overwrite is involved. Later independent checkouts require explicit snapshot exchange or validated additive backup restore, and binary Git conflicts cannot be automatically merged.

`node launcher/restore-snapshot.mjs <snapshot-file> [--workspace main|demo]` replaces one workspace database with a snapshot. It resolves the data directory like the server, including `MASTERQC_DATA_DIR`. It refuses to run while anything accepts connections on `127.0.0.1:4173`, or while `-journal`, `-wal`, or `-shm` files exist beside the database. It copies the snapshot to a temporary file in the data directory and runs SQLite's `PRAGMA integrity_check`. It then opens the copy with the current adapter and service, which may upgrade an older layout on that copy. Business validation runs with trusted attachment metadata, every payload is verified one row at a time for MIME type, size, and SHA-256, and every historical source PDF is checked against its recorded SHA-256. The command then copies the validated file beside the live database, keeps the previous database with a hard link under `<database>.before-snapshot-restore-<UTC timestamp>.sqlite`, and renames the copy over the live file. A failure at any step leaves the live database unchanged and returns a non-zero status.

## Separated Attachment Persistence

The SQLite adapter stores business records as units. Eligible arrays keep one row per record in `qc_records`, and every other value is a whole unit in `qc_units`; each transaction rewrites only the rows whose serialized JSON changed. Attachment Data URLs and trusted content metadata stay in `qc_asset_payloads`. Startup verification iterates payload rows one at a time, but its peak memory still grows with the stored total; full state and JSON backup reads return every payload only up to the full-read limit. SQLite reads the columns after a Data URL by walking its overflow pages, so payload metadata is cached per payload generation and ordinary saves do not depend on total attachment size. Reads that touch several rows run in one read transaction. Stable asset IDs resolve their content references. Full reads and backups reconstruct the established aggregate format; lightweight reads and ordinary commands do not join or rewrite all attachment payloads. Incoming payloads receive complete validation, while validated stored payload metadata supplies MIME, decoded size, digest, and content generation. Business graph, ownership, category, extension, and size checks always run. Trust is invalidated when content generations or another database connection change stored content; restore validates all incoming content. Migration retains an independent recovery snapshot, preserves the domain revision and original full-state shape, and commits conversion atomically. The `storage_format` marker in `qc_adapter_meta` records the layout (absent means the previous single-row format); new databases start in record storage, and reopening a converted database changes nothing. Earlier releases reject a converted file on initialize. DELETE journaling and FULL synchronization remain required.
