# Local App Contract

Status: 2026-09-30 implementation contract, with same-computer shared SQLite storage. User decisions in requirements.md take precedence. The first build connects catalog, standards, purchasing, inspection, issues, library, reporting, and backup through one durable local workflow.

## Public interface

`core/qc-service.js` exports `createQCService(adapter, options?)` for server-side business execution. `core/qc-app.js` composes and exports an HTTP service facade as `qcService` for browser callers. The facade preserves the public service interface. All public operations are asynchronous:

- `initialize()` opens storage and creates the empty catalog state only if absent. Existing imported history is upgraded atomically to canonical historical batches once. It applies a narrow, audited, idempotent status correction to the two exact AP `25.10.29` PDF-derived version IDs, guarded by family, label, source marker, and prior status. When a matching recorded source entry is present and verified, it moves linked documents to that entry, removes the duplicate from active `versions`, and retains its full superseded record in optional merge evidence. A missing recorded target leaves that pair unchanged for older PDF-only workspaces. It also removes the single authorized S15 trial source version only when ID `lark:recvwbnjOo2r4P:s15`, source ID `recvwbnjOo2r4P`, family `s15`, label `26.09.05`, description `fefe`, and empty specs and attachments all match. If a batch or other dependency references that version, initialization rejects without a cascade or partial deletion. No other versions are archived or deleted by date, status, or label. No sample orders, batches, results, or signatures are installed automatically.
- `getState()` returns an isolated state snapshot.
- `command(type, data, expectedRevision)` validates current state and writes atomically; returns `{ entityId, revision }`. A supplied stale revision rejects with an actionable reload message. Frontend supplies its current snapshot revision.
- `getBatchWorkspace(batchId)` returns the batch, a query-only `displayNumber`, related entities, resolved product allocations, rows, release blockers, and resolved batch attachments. `displayNumber` is outside the persisted batch object. Operational rows include their product label, quantity and locked version, legacy photos, resolved `{ videos, procedures, log }` attachments, every linked Issue with its resolved evidence files, and up to four saved older results for that product variant. Historical workspaces preserve source values and provenance; unknown related entities remain null.
- `resolveBatchDisplayNumbers(state)` in `core/qc-batch-display.js` returns a `Map` from batch ID to staff-facing name without changing state. It resolves collisions against the complete batch collection before any UI filtering or sorting.
- `getPurchaseOrderProgress(orderId)` returns `{ order, lines }`; each line includes `variant`, `orderedQty`, `releasedQty`, `remainingQty`, `excessQty`, and contributing `batches`.
- `exportBackup()` returns a JSON-serializable `{ format: 'masterqc-web-backup', formatVersion: 1, exportedAt, state }`, including attachments.
- `importBackup(backup, expectedRevision)` validates the full graph before an atomic, additive import. Exact verified AP duplicates in older backups are reconciled into an available matching recorded entry. It filters the exact guarded S15 trial record from older backups and applies the same dependency check to an existing active copy, so the trial cannot be restored; if referenced by a batch or other dependency, restore rejects without a cascade or partial deletion. Other identical IDs with identical content are skipped; conflicting IDs reject without changes. This operation never clears or overwrites other existing data. It returns counts and the new revision.

Errors throw `Error` with English user-facing messages. No DOM or browser dialogs belong in core. Empty strings, nulls, fractions, non-finite quantities, and invalid references must be validated before committing. Reads return copies. Dates use `YYYY-MM-DD`; event timestamps use ISO timestamps.

`core/qc-service.js` also exports attachment limits: `PHOTO_MAX_BYTES` (5 MiB), `DOCUMENT_MAX_BYTES` (10 MiB), `ASSET_TOTAL_MAX_BYTES` (30 MiB decoded payload), and `BACKUP_MAX_BYTES` (50 MiB serialized JSON). `core/qc-app.js` exports `createDemoQCService()` for the separate, explicitly labelled demo workspace.

## State

SQLite stores one transactional aggregate per isolated workspace. The server reads the current aggregate and validates expected revision and related facts inside a transaction before committing the next aggregate. Attachments remain bounded data URLs; larger-scale entity and attachment storage is a future adapter change. The previous version-2 IndexedDB `settings` and `qcState` stores remain untouched for the initialization draft and explicit legacy migration. Migration uses the full backup format and existing validated additive restore, preserving identifiers and evidence; it does not silently replace a populated SQLite workspace.

State is `{ schemaVersion: 1, revision, families, variants, versions, orders, batches, issues, assets, audit, versionMergeEvidence? }`. Collections are arrays; IDs are stable strings generated with UUIDs. Initial catalog contains families `s11-s14` and `s15`, models S11–S15, and standard-red and Yellow variants. Display names omit Red. The latest-published query remains published-only and sequence-based. The new-batch default considers existing `recorded`, `published`, and `superseded` versions, ordered by `effectiveDate` or a recorded entry's source effective timestamp, with sequence as a tie-breaker; mutable `draft` versions are excluded.

- Family: `{ id, name, models: string[] }`.
- Variant: `{ id, familyId, model, color, label, active }`; `label` is the displayed name. Extra minor variants may be added with a distinct label.
- Operational version: `{ id, familyId, label, sequence, effectiveDate, status, notes, items, createdAt, publishedAt }`. `status` is `draft`, `published`, or `superseded`; `sequence` is a positive integer unique within the family and determines numeric ordering. Published and superseded versions are immutable. Published-version ordering continues to use sequence for its existing query. Superseded versions are eligible for new batches, including when `publishedAt` is null. An imported Lark source version uses `status: "recorded"`, `sequence: null`, `effectiveDate: null`, `createdAt: null`, `publishedAt: null`, and `items: []`; its original facts live in `source` and `sourceRows`. These records are immutable evidence, not Web drafts or published standards. Their source effective timestamp, raw status, exact label, change description, linked spec values, nulls, and attachments metadata remain unnormalized in the source payload. Recorded versions have no operational sequence but are eligible for new batches: core projects the linked source rows into the batch snapshot without changing `items`, `source`, or `sourceRows`, and without publishing or rewriting the record.
- Standard item: `{ id, key, no, title, titleZh, specification, specificationZh, devices, factory, stage, models, samplingPercent, recordingRule, important, timeSeconds, procedureUrl }`. `models: []` means all models in the family. `key` is the stable historical comparison identity. Sampling is numeric and independent of the descriptive recording rule. Item IDs remain stable through editing/cloning unless explicitly adding a new item.
- Order: `{ id, number, date, supplier, notes, lines, createdAt }`; line: `{ id, variantId, orderedQty }`. Order numbers are unique. Referenced lines cannot change variant or be removed.
- Operational batch: `{ id, number, orderId, products?, lineId, variantId, familyId, quantity, factory, stage, lotNumber?, countForPO, versionId, versionLabel, date, recorder, notes, status, rows, createdAt, releasedAt, attachmentIds? }`. Number is unique and remains in the existing saved field. Core generates it for a new command with an omitted or blank number as the distinct product models, sorted deterministically and joined by `+`, followed by `-YYYYMMDD-<normalized factory>-<normalized stage>`. A case-insensitive collision with stored numbers or resolved historical display names adds the first available `-01`, `-02`, and subsequent suffix. Legacy commands may still supply an explicit number; saved values are not rewritten. New batches contain `products: [{ lineId, variantId, familyId, quantity, versionId, versionLabel }]`, with unique lines from one PO, variants of one model, and a safe positive integer quantity per color. Existing mixed-model records remain valid; the restriction applies to new commands only. The canonical `createBatch` command supplies one top-level `versionLabel`; core resolves that exact common label to each selected family's eligible version entity and saves those family-specific IDs in the product allocations. The top-level quantity is their sum. Single-product identity and version ID mirror that product when there is exactly one; those identity fields and `versionId` are null for a multi-product batch. A new shared-version batch retains its common `versionLabel` at the top level. Older mixed-version multi-product records retain a null top-level label and their independent nested version IDs. Existing records without `products` retain their original single-product fields. Core normalizes both shapes through pure queries without rewriting saved records. New batches need no physical lot identifier; preserved non-empty legacy lot values retain their existing duplicate-counting checks. For every new batch, core derives `countForPO` from the stage: OQC is true and IQC is false. Callers cannot opt out of counting a new OQC batch. Previously saved flags remain unchanged. A released counting batch contributes each product's quantity to that PO line. Omitted `attachmentIds` in older data means no batch documents. Attachments are optional and independent of row photo ownership.
- Batch row: all standard-item fields plus `{ inspectedQty, defectiveQty: null, actualTimeSeconds: null, remarks: '', savedAt: null, photoIds: [] }`. New product rows also contain `{ productLineId, sourceItemId }`: a fresh unique row `id` owns results and evidence, while `sourceItemId` preserves the original locked standard-item identity. New rows may also have `attachmentIds: { videos: id|null, procedures: id|null, log: id|null }`; older rows omit it and remain unchanged. Each slot owns one `rowAttachment` asset and cannot share it with another row or Issue. `inspectedQty = ceil(product.quantity * samplingPercent / 100)` is locked with the row; legacy rows use their single batch quantity. Complete row saves require finite numeric `actualTimeSeconds >= 0`, allowing decimals. Autosaves accept null measured time and defective quantity for incomplete rows, preserve remarks for old records and callers, and clear `savedAt` while either numeric result is absent. A legacy row that truly omits `actualTimeSeconds` may receive an autosave without that field; core preserves the omission and its historical completion rule. Current rows with an explicit measured-time value, including `null`, require the field in every autosave. Partial values remain valid backup data; only completed rows provide release, issue, and history eligibility. It is an entered result independent of the locked standard `timeSeconds`. Older rows and backups may omit it; missing values are not filled from the standard or zero. New issue snapshots and operational reports preserve the entered time. Defective rate is derived by core; zero inspected quantity gives null rate. Product allocations, standards, and batch identity/quantities are immutable after creation; recorder, date and notes remain editable until release.
- Issue: `{ id, number, title, description?, requestId?, requestFingerprint?, attachmentIds?, batchId, rowId, sourceSnapshot, status, owner, disposition, confirmations: ['', '', ''], discussion, createdAt, closedAt }`. Every newly created Issue requires at least one uploaded raster photo; a general file or legacy row-photo snapshot alone does not satisfy the requirement. Existing Issues and backups may omit Issue attachments and remain unchanged. Standalone issues use null source IDs; optionally associate them with a batch. New batch-linked snapshots contain `products: [{ lineId, variantId, variantLabel, quantity, versionId, versionLabel }]`; single-product metadata is null for a multi-product batch. A row-linked snapshot additionally preserves the actual product's line, variant, family, quantity and version within `sourceSnapshot.row`. Existing single-product snapshots remain valid. Several Issues may link to one batch and row when each is created with a distinct request ID; a matching request ID and creation payload returns its original Issue on retry. A mismatched reuse of the ID is rejected. Callers without a request ID retain the legacy singleton behavior for a batch and row. Additional Issue attachments can be added later. Each new discussion entry requires a manually entered, trimmed nonblank `authorName` of at most 200 characters. Legacy entries may omit `authorName`; preserve them without backfilling a name. If present, the stored name must be valid nonblank text. Closing requires owner, disposition and all three names, then an explicit action. Closed issues and Issues linked to released batches are read-only.
- Asset: `{ id, name, mimeType, dataUrl, kind, batchId, rowId, versionId, createdAt, issueId?, category? }`. Existing `photo` and `document` kinds remain valid. A `rowAttachment` has `batchId`, `rowId`, and category `videos`, `procedures`, or `log`; it exclusively owns that inspection-row slot. An `issueAttachment` has `issueId`, and its nullable batch and row IDs must match its Issue; category is `photo` or `file` and preserves the applicable per-file limit. Library documents may associate with a version. Supported general files include PDF, PNG/JPEG/WebP/GIF, text/CSV/Markdown/log, DOC/DOCX/XLS/XLSX/PPT/PPTX, ZIP, and MP4/MOV/WebM. Active web content, executable files, SVG, and macro-enabled Office formats are rejected. Keep 5 MiB per photo, 10 MiB per general file, 30 MiB total assets, and 50 MiB per backup; no attachment-count cap is imposed.
- Optional version merge evidence: `{ id, targetVersionId, version }[]`. Each entry preserves the complete superseded PDF-derived operational record removed by the exact AP merge. This backup-only collection is not shown as a separate version or selectable batch choice; older state and backup files may omit it.
- Audit entry: `{ id, at, action, entityId, summary }`. Business mutations append an event for local traceability; this is not authenticated identity verification.

## Historical batches and source evidence

The optional `state.history` object contains `sources`, `inspections`, and `anomalies`. States and backups without this object remain valid. These collections preserve transcription evidence. Each imported inspection also has a canonical entry in `state.batches`, shown in the same Batches workspace as newly entered inspections. The evidence collection is not a separate user-facing PDF history module.

Historical batches have `kind: 'historical'`, `status: 'historical'`, and `historyInspectionId` equal to their stable source inspection ID and batch ID. The persisted `HIST-...` archive number remains an internal compatibility value for existing backups and validation; it is not the staff-facing name. A shared core display query resolves concise names without modifying persisted state: prefer an explicitly transcribed original batch number, otherwise model/family-date-factory-stage, with short numeric suffixes only for actual collisions. Existing operational batch numbers remain unchanged. Lists, detail headings, search, and reports/CSV use the same resolved name. Family, product label, model, color, factory, stage, date, printed version label, quantity, recorder, notes, and row results preserve the source. Unknown order, order line, variant, design-version entity, and physical lot links remain null. `countForPO` is false and `releasedAt` is null. Historical batches cannot be released or edited through operational result commands. Their preserved evidence must match the original source record.

`attachmentIds` links document assets to batches. Several batches can reference the same original PDF asset without copying the file bytes. New native batches need no attachment. Supplementary attachments may be added to historical batches; their original source PDF association remains intact.

`importHistory(package, expectedRevision)` accepts the compatible wire format `format: 'masterqc-pdf-history'`, `formatVersion: 1`, and arrays `sources`, `inspections`, and `assets`, with optional `versions` (unpublished source-reference drafts) and `anomalies`. Validate the complete graph and original-file SHA-256 values before an atomic, additive import that also creates historical batches. Identical records are skipped; conflicting records reject without replacement. Full-app backup and restore preserve evidence, canonical batches, and attachments. Older history-only backups are upgraded without a manual re-import.

- Source: `{ id, fileName, sha256, pageCount, family, assetId }`, with optional extraction provenance. `family` is `s11-s14` or `s15`; `assetId` points to an original PDF document in the existing asset collection.
- Historical inspection: `{ id, sourceId, page, printedVersion, printedDate, date, productLabel, model, color, factory, stage, batchQuantity, recorder, notes, rows, anomalies }`. Unknown source facts can be null. This schema deliberately permits mixed or unidentified products and source-specific inspection stages without inventing an operational product variant.
- An optional `inspection.originalBatchNumber` may hold an explicitly transcribed source batch number for display. The current 89-record import contains no such field. Display queries never infer this value from PDF filenames, raw text, or technical archive identifiers.
- Historical row: `{ no, title, specification, devices, samplingPercent, recordingRule, timeSeconds, important, sourceInspectedQty, defectiveQty, sourceDefectiveRate, remarks, raw }`. Source values are retained; source inspection quantities and printed percentages are not replaced with formula results. An optional `status: 'missing-from-source'` requires null result fields and `missingEvidence` identifying the applicable check's source.

The Batches list provides status/family/factory/stage filters without an Attachments column. Operational inspection rows each have one Attachments column with one file slot for Videos, Procedures, and Log; historical batch detail retains its source and supplementary batch attachments. Historical batch detail provides the recorded inspection table and secondary source provenance; any formula comparison is separately labelled. The old `#/history` route redirects to Batches. User-entered new batches continue to use the existing operational commands and validation rules.

The bundled Lark history remains served from the exact allowlisted static path, `/data/lark-import/version-history.v1.json`; the server does not expose the temporary raw exports. The retained core command imports the raw package while excluding the one authorized S15 trial record; the package file remains an unchanged 23-entry source capture. The Standards page exposes no source-import controls. Full backups and additive restore preserve recorded-version metadata and raw source rows except that exact trial record. Previously downloaded backups may still contain it; restore omits the guarded record and keeps other valid data, and rejects rather than cascading if a dependency references it. Backups created before Lark history import remain valid and do not acquire source entries unless the command is explicitly run.

The main page shows usable navigation, storage status, an empty-state starting path (add standards, create order, create batch), and in-context errors. The operational entry workspace uses a bilingual table grouped by product, with task, criteria, results, and row attachments visible together; it omits a Remarks textbox and preserves existing remarks in saved and historical records. Auxiliary equipment, frequencies, procedure, and saved history are disclosed within the row. Historical and report tables retain their source layout. White bordered fields are editable; calculated quantities and rates are read-only. Each inspection row owns its attachments. Batch reports use saved facts only, preserve saved history, issues, source photo semantics, row attachments, and issue evidence, and print with CSS for the selected batch; unsaved browser drafts remain in tab memory and are not included. Backups are downloadable JSON with attachments and additive restore validation.

Operational workspace rows may expose query-only `displayImportant` and `importanceEvidence` metadata. Explicit source importance or a locked ordinary standard takes precedence. Recorded rows whose source omitted importance can be highlighted only when matching original-PDF standards agree, scoped by family, model context, factory, stage, criteria, equipment, sampling, and recording rule. Ambiguous or missing evidence does not imply importance. These display fields do not change persisted `row.important`, inspection calculations, release rules, backup data, or schema.

## Shared Local Service Contract (2026-09-30)

- The browser uses same-origin JSON HTTP calls. The server executes existing core methods; browser code cannot directly write SQL or replace state.
- Production and demo workspaces are explicitly allowlisted and separate. The server binds to `127.0.0.1:4173`, checks Host and Origin, and rejects unsupported operations, oversized payloads, and invalid JSON request types.
- Every browser mutation sends its observed revision. A stale revision fails without committing; clients must reload before retrying. Reads, exports, and legacy migration reads do not modify the source IndexedDB.
- Legacy migration reads this browser's existing aggregate, validates and serializes a full backup, then restores it additively through the shared service. Original initialization settings stay browser-local.
- Saved records survive browser reload and server restart. Batch inspection and metadata inputs autosave; invalid, failed, or in-flight edits remain tab-local until acknowledged. Other forms retain their explicit save actions. Local service availability is required for reads and writes; failures must not fall back to a disconnected browser database or report a successful save.

## Portable Project Database

Default production persistence is `data/workspace/masterqc-main.sqlite`. The file includes the complete aggregate and attachment payloads and is eligible for Git. Demo data and temporary SQLite journal files remain ignored. A `MASTERQC_DATA_DIR` override changes the storage directory without rewriting or importing another existing database. The workspace directory is never statically served.

SQLite DELETE journaling with FULL synchronization retains completed commits in the main file. Stop the service before copying, committing, pulling, or replacing it because file-copy tools and Git do not take SQLite transaction locks.
