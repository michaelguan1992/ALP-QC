# MasterQC Web Local Edition

## Start and choose a workspace

Start with `Start-Mac.command` or `Start-Windows.cmd`, or run `npm start`. Keep the startup terminal open. Open `http://127.0.0.1:4173/` for the working database. Use `?workspace=demo` for a separately stored rehearsal workspace. The original table prototype remains at `/frontend/prototype.html` and resets on refresh; the complete app saves to the local SQLite service. Chrome and the in-app browser on this computer share the same selected workspace.

## Set up standards

Catalog separates product families, models, and variants. S11-S14 share a family; S15 has its own. Standard red products omit the color suffix, while Yellow variants retain it. Minor variants can have distinct ordering identities without introducing another inspection family.

Existing product families already have standards, and new-batch entry stays available. Recorded, published, and superseded versions can supply a new batch; the default is the latest version label that is common and ready for every selected product, with effective dates and source timestamps determining chronology and sequence breaking ties. Staff can choose another eligible shared label manually. That label resolves to the selected family’s own version entity, so different families can retain distinct version IDs under the same displayed label. Recorded source entries stay read-only: their linked source rows are projected into the batch snapshot without republishing the source record or filling its empty `items` field. Create and publish a Web draft when staff need to add or revise operational standards. Each AP `25.10.29` family has one recorded entry with its original PDF attached. The verified PDF-derived duplicate is removed from the active version list and retained in backup merge evidence; the recorded source facts remain unchanged.

Each standard item defines factory/stage applicability, optional model applicability, inspection percentage, recording instructions, and inspection requirements. AP uses OQC only. The inspection percentage determines the automatic sample quantity. Recording instructions do not change that quantity.

Each family has one **Versions** list. Recorded source entries appear first in source effective-date order, followed by operational versions in numeric sequence order. The two verified AP `25.10.29` PDF duplicates are merged into their matching recorded entries, so each family has one visible entry for that label and its PDF remains attached. Recorded cards preserve source facts, draft cards retain edit, publish, and item-view controls, and published and superseded cards use a compact read-only layout with no right-side actions or item table. A superseded card shows `Status: 已作废 Superseded`; it cannot be edited or republished, but can be selected for a new batch. Published and superseded cards show their label, status, effective date, attachments, and a **Change description** disclosure. The disclosure shows ordinary business notes and stays blank for generated reference notes or empty notes; saved notes are unchanged. Extraction origin, provenance, anomaly details, and raw revision fields are omitted from the business view. Sequential numbered points in a recorded change description are separated onto lines for reading, while the saved source text remains unchanged. A label of `VENTUS` is hidden from this page after trimming and case-insensitive comparison; the version remains in workspace data and backups. Generated reference notes beginning `Historical source reference draft.` or `masterqc-ap-oqc-reference-25.10.29.` are omitted from cards only; ordinary staff notes remain visible and editable.

Each recorded, draft, published, or superseded version card places its attachment control beside the version label. Use **Upload attachment** when none is linked. After upload, each filename appears as a compact link; open it to preview the PDF, image, or text, download it, or delete a mistaken upload. Delete asks you to confirm the filename. Upload stays hidden while any documents remain and returns after the last one is removed. Shared historical or batch evidence stays linked to its record when removed from a version. Uploads use the same file types and 10 MiB per-document / 30 MiB total limits as the library, which continues to show linked files.

## Order and inspect

Create a purchase order with one line per separately tracked product variant. Select a PO, add one or more colors of one model from its lines, and enter each product's quantity. Choose one design-version label for the batch and the shared factory/stage. The label defaults to the latest common ready choice and may be changed to another common eligible label. Each product's version record and inspection rows remain family-specific, and sample quantities use that product's quantity. Enter the date and recorder. The system generates the batch name from the selected model, date, factory, and stage, adding a numeric suffix only when that name is already in use. There is no physical-lot field, final-shipment selection, or batch reinspection workflow.

The batch captures its applicable standards and sample quantities when created. Later version changes do not alter it. Sample quantities round up to whole units. The entry table groups rows by product and places calculated inspection quantity, defective quantity, and rate in Results beside remarks and row photos. Details starts expanded and contains specifications, equipment, and frequencies. Results includes defect-rate History and an editable Time in seconds; enter a nonnegative number, including zero or decimals. Use Batch details to edit the date, recorder, or batch notes. Defective quantities, Time, remarks, and batch details save automatically after a short input pause or when leaving a field. Partial rows also persist; blank numeric results remain blank until entered. Attach evidence separately to each row. Green identifies important checks, not successful results. Where a recorded source omitted importance, the display can recover it from agreeing original PDF checks with matching standards and applicability; this does not rewrite saved inspection facts.

Raise an issue from an inspection row to preserve its source facts and evidence references. Issues can also be entered independently, with optional batch association. Record discussion separately from formal disposition. Enter **Your name** with each new discussion entry; the saved entry displays that name. A blank name prevents adding the discussion and leaves the draft available. Enter the disposition owner and three manual confirmation names, save, and explicitly close the issue. Names are staff-entered confirmations, not authenticated digital signatures.

Release remains a separate action. Complete every row, provide the recorder, and close linked issues before release. Released records are read-only. Every new OQC batch contributes each product's full quantity to its PO line after release. IQC and historical records do not contribute; inspection sample quantities are not fulfillment quantities. Previously saved counting choices remain unchanged. Separate variants show separate shortages and excess quantities.

Use **Delete** beside **All batches** and **View report** to remove an unreleased operational batch after confirmation. Linked Issues or independent evidence references prevent deletion. Shared documents stay in the library. Released and historical batches remain protected.

## Batch reports and documents

Open a batch detail and choose **View report** to see its read-only saved facts, inspection results, historical comparisons, linked issues, and row photos. Operational Draft or Released status remains visible in report detail. Opening the report first finishes pending autosaves. Persisted partial results appear in the report. Invalid values or failed saves retain the local edits and block navigation until resolved. Choose **Back to batch** to return to the same batch. Use **Print / save as PDF** for the browser's print dialog or **Download CSV** for tabular results. Historical comparisons use saved prior results; empty histories remain empty.

The library stores local documents and can associate them with a design version. Photo evidence remains attached to the specific inspection row. Exported backups contain attachment data, not just filenames.

## Historical batches and attachments

Use **Batches** for both imported inspections and newly entered batches. Filter by family, factory, or stage, or search for the batch you need. Click a batch row to open it (or focus the row and press Enter or Space). Attachment controls open or download the file separately. The list shows Batch, Purchase order, Total quantity, Date, and Attachments, with Attachments last. Product / model and Factory / stage are omitted from the list; product search and factory/stage filters remain available. Open an imported record to see its original quantities, defects, notes, printed version, and distinct printed dates. The **Attachments** column and batch detail provide its original PDF, including signatures, photographs, and the complete layout.

Batch names show product/model or family, date, factory, and stage, for example `S15-20260521-UI-OQC`. An explicitly recorded original batch number takes priority when available. Only matching names receive short suffixes such as `-01` and `-02`. Original-PDF provenance and source page numbers appear in the attachment/source details; imported batches have no separate Historical status label. Operational Draft/Released status remains available in batch detail. The same names appear in batch reports and CSV exports.

Attachments are optional for newly entered batches. Batch documents and inspection-row photos have separate ownership: a PDF can describe the whole batch, while a row photo remains evidence for that particular check.

Use **Open PDF** in the list, or **Open** beside a batch attachment, to preview the document inside the app. **Download** saves the original file. The original imported PDF remains linked as source evidence; removing a supplementary attachment only removes its batch link and keeps the file in the library.

Historical source values are read-only. A separate formula comparison may differ from the original inspected quantity; the original value is preserved. A blank result means no result was recorded, not zero defects. Checks added to complete a same-version checklist are marked as absent from the original sheet and retain empty results with a source explanation.

These historical sheets do not count toward purchase-order fulfillment. They may contain mixed models, partial shipments, or no complete order information. The AP `25.10.29` PDFs remain linked to their matching recorded standards entries; their removed operational duplicates are retained in optional backup merge evidence, not as selectable versions. See [Original PDF Import](pdf-import.md) for the evidence rules.

The historical batch import action in Batches accepts a prepared source package, validates its documents and records, and skips identical records on repeat import. Existing imports automatically appear in Batches after the application upgrade; no re-import is needed. Use full backup and restore to move the complete workspace, including historical batches and their attachments, to another computer. Browsers on this computer already share the local service workspace.

## Backup and recovery

Open **Backup and restore** at the bottom of the sidebar. Save your edits, then choose **Download full backup** to export the saved workspace records and attachments. For a separate backup handoff, share this file with a collaborator who has a compatible app; they can select the file under **Restore into this workspace**, then choose **Validate and restore backup**. Unsaved edits and application code are not included in the backup.

Export backups regularly and before changing computers or the service data directory. A backup belongs to the selected workspace. Restore validates the file and all references, then adds missing records. Identical records are skipped; conflicts reject the import rather than overwrite current facts. Older backups may still contain the S15 `26.09.05` trial entry; restore omits only that approved entry from the active workspace and restores other valid records. If a batch or other dependency refers to it, restore rejects rather than deleting that dependency. The downloaded backup file itself remains unchanged. Use `http://127.0.0.1:4173` to return to the shared local database from any browser on this computer. Saved changes survive closing the browser and restarting the service; unsaved form drafts remain tab-local.

The first edition limits individual photos to 5 MiB, documents to 10 MiB, aggregate decoded attachments to 30 MiB, and serialized backup files to 50 MiB. Save smaller images when necessary. Browser quota failures are reported instead of being treated as successful saves.

The project folder includes the saved production database at `data/workspace/masterqc-main.sqlite`. Stop the service before copying, committing, pulling, or replacing it. A collaborator starting that project sees its saved snapshot, including attachments. Later changes on separate computers remain independent; Git does not provide live synchronization or automatic database merging. Download a full backup before applying another snapshot. The configured GitHub repository is public, so uploading this database exposes all its records and attachments. Windows runtime verification must be completed on a Windows computer; Mac checks do not verify it.

## Migrate the Older Browser Workspace

In the browser containing your existing records, first download a full backup. Start the updated local service, open **Backup and restore** in that browser, then choose **Migrate data from this browser**. This reads the browser's legacy IndexedDB records and restores them additively into the selected SQLite workspace. Alternatively, select the exported JSON backup and choose **Validate and restore backup**. Both paths validate references and attachments; matching records are skipped and conflicts stop the import without partial changes.

Verify the record counts and open an attachment in both browsers after reload. Keep the downloaded backup and source browser data. Legacy IndexedDB is not cleared, and later SQLite saves are not copied back into it. The preserved initialization draft continues to be local to its original browser.

When another browser changes the workspace, the page offers a reload before the next save. Save your drafts or explicitly choose how to handle them; an outdated page cannot silently overwrite newer saved records.
