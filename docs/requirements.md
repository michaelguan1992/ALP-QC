## Versions, Issues, and Signatures

- A new Web batch has one design-version selector for the whole batch. It defaults to the latest eligible label that is common and ready for every selected product model and family, and allows manual selection of another common label. That label resolves to each family's own immutable version entity, so the saved product allocations can have distinct version IDs. Eligible versions are immutable recorded source entries, published versions, and superseded versions; mutable drafts are excluded. A version whose projected applicable items cannot be locked unambiguously is not selectable. This decision overrides the Lark edition's behavior of making no default selection.
- Compare eligible versions by effective date, using a recorded entry's preserved source effective timestamp when its operational `effectiveDate` is null. Use operational sequence only to break equal-date ties; do not infer version order from label text or file modification time. The published-version sequence query remains available for its existing published-only uses.
- An inspection issue can be converted to a standalone Issue; repeated saves must not create duplicate Issues. Issues can also be reported independently.
- Discussion and formal disposition records are stored separately. Each issue can be traced to its source inspection and evidence.
- Confirmed on 2026-10-01: Issue detail shows uploaded Issue photos directly in Evidence, with preview and download available. Display immutable source-row photos separately only when present; omit an empty Source photos section. New Issue creation optionally accepts an Initial disposition owner, saved in the existing owner field and editable through subsequent disposition saves. Keep the reporter name separate and required.
- Confirmed on 2026-10-01: every newly created Issue requires the submitter's manually entered name, displayed as Reported by. Reject missing or whitespace-only names before creation, persist the trimmed name, and keep it separate from disposition ownership and discussion attribution. Existing Issues and backups without a submitter remain readable without inventing a name. The Issues list opens an Issue by clicking anywhere on its row or pressing Enter or Space on a focused row; omit the separate Open button and action column.
- Confirmed on 2026-10-01: Issue detail includes an explicit Delete issue action with confirmation. Deletion removes the Issue and its owned evidence, preserves inspection rows, source photos, shared files, and an audit entry, and does not automatically release a batch. Issues linked to released or historical batches remain protected to preserve those recorded facts.
- Updated on 2026-10-01: Issue detail provides one **Save changes** action for the disposition owner, formal disposition, and all three confirmation names. Input, pause, change, and blur never save these fields. Accept partial entries and cleared values. Preserve focused inputs and newer typing during writes; show Saved only after server acknowledgment. Unsaved edits require an explicit Save, Discard, or Cancel choice before dialog dismissal, navigation, or Issue closure. Failed or stale saves retain the draft. Discussion entries and attachment changes remain independent explicit operations; they do not silently save disposition drafts.
- Confirmed on 2026-10-01: each new discussion entry requires the contributor's manually entered name. Reject missing, blank, or whitespace-only names with a clear error, preserve the unsubmitted draft, and display the saved name with that entry. Keep older discussions without names unchanged and readable. This is per-entry attribution, separate from disposition ownership and closure confirmations.
- The initial trust-based approach retains three blank signature fields for users to enter the voters' names. Do not add login identity verification or server-side vote validation, and do not describe a manually entered name as an identity-verified signature.
- The rest of the closure flow follows the previous plan: the disposition owner, a formal disposition record, and confirmation from all three people must be present before manual closure. The third signature does not close the issue automatically. Any linked issue that remains open blocks batch release; closing all issues does not release the batch automatically. Details of the interaction will be refined during implementation.
- Do not add automatic reminders that continue after the Web page is closed or background scheduled tasks for now.
- Preserve the history of original files, archived reports, and saved batch facts. Generate the in-app per-batch report from saved facts without storing each report as a separate archive or listing reports as a standalone workspace. New standards or formulas must not silently overwrite archived facts.

## Design Versions, Standards, and Batch Inspections

Confirmed on 2026-09-26. Domain terms are defined in [the glossary](../CONTEXT.md).

- Each design version defines one complete inspection standard set containing multiple inspection items. Applicable items differ by factory and inspection stage (IQC or OQC); these are selections within the version's complete set, not independently versioned standards unless a later decision establishes otherwise.
- At creation, one batch-level version label resolves to the selected family's eligible version entity for each product, then locks that product's applicable inspection standards for the batch factory and inspection stage. The default is the latest common ready label, with older common labels selectable as described above. Later version changes must not silently change the standards locked for an existing batch.
- New-batch entry remains enabled for existing product families, which already have current standards. Recorded source entries can supply a pure projection of their linked source rows into the new batch snapshot; this does not fill or rewrite the recorded entry's empty `items`, change its raw source, or publish it. Ordinary batch creation does not require republishing imported standards or replenishing source items.
- In the user's example, AP performs OQC only. A new AP OQC batch defaults to the latest common design-version label with lockable AP OQC items for every selected product.
- The same inspection item has separate inspection records across different batches. Results from one batch must not overwrite another batch's results.
- Confirmed on 2026-09-28: inspection quantity is calculated from batch quantity and the applicable inspection sampling percentage, and is not manually editable. The recording percentage is separate and does not determine inspection quantity. The prototype rounds fractional quantities up to whole units (for example, 423 units at 10% gives 43); this rounding convention is an implementation assumption pending review. Defective quantity and remarks remain editable, and defective rate is derived from the calculated inspection quantity.
- Confirmed on 2026-09-30: batch reinspection is neither needed nor supported. Do not add reinspection rounds, attempts, or duplicate-batch workflows. Ordinary correction of draft results before release remains available.
- The first-edition implementation conventions below define numeric version ordering, rejection of empty applicability, and copied batch snapshots while preserving the confirmed lock-at-creation rule.
